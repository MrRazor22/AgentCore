Abstract
Large language model agent frameworks increasingly combine model invocation, tool execution, context
management, guardrails, persistence, orchestration, observability, and multi-agent coordination. This paper
studies a narrower architectural question: whether a turn-based, tool-using agent can be decomposed
around a small set of stable semantic primitives while expressing most cross-cutting variation through
policies, composition, and contract-preserving layers. We call this approach primitive-first architecture. The
revised manuscript makes four changes motivated by critical review. First, it no longer treats the three-axis
model as a universal theorem. Instead, it defines an independently testable capability universe for the
studied agent class and asks whether reasoning, acting, and remembering form a minimal generating set
under explicit criteria. Second, it separates structural minimality from behavioral equivalence: removing a
primitive must be tested by controlled ablation, not inferred from interface elegance. Third, it makes
architectural locality—the amount of unrelated structure disturbed by a requirement or fault—the primary
empirical construct rather than raw LOC. Fourth, it specifies a reproducible cross-framework protocol
covering matched extensions, sequential requirement evolution, static architecture metrics, AI-assisted
implementation, and fault locality. AgentCore is used as a reference implementation, not as the source of the
capability definition. The supplied evidence currently establishes the architecture and protocol, but does not
establish causal superiority: the cross-framework experiments remain to be executed. This distinction is
explicit throughout the paper.

1. Introduction
Agent frameworks are becoming software platforms rather than thin wrappers around model APIs. Current
systems expose tools, sessions, context providers, middleware, workflows, handoffs, tracing, persistence,
and safety controls. Contemporary documentation makes the diversity visible: OpenAI's Agents SDK centers
agents, tools, handoffs, guardrails, and sessions; Microsoft Agent Framework combines agents, middleware,
context providers, and graph-based workflows; DeepSeek's Cordis develops a more general context
paradigm for dynamically composable components. [1–4]

The architectural question in this paper is deliberately narrower than “which framework is better?” We ask
whether a common class of turn-based, tool-using agents can be represented using a small set of semantic
contracts, and whether that representation changes the locality of subsequent software changes. The key
distinction is between a primitive and a mechanism. A primitive is a stable behavioral boundary required by
the target execution model. A policy is replaceable decision logic inside or around a primitive. Composition
combines existing primitives or agents. A layer preserves a contract while changing behavior around one
existing component.

The proposed primitive-first model uses three contracts: reasoning, acting, and remembering, represented in
the AgentCore implementation by ILLM, IToolbox, and IContext. The claim is not that every possible agent
system must have exactly three primitives. That stronger claim is neither necessary nor justified by the
current evidence. The research claim is conditional: for a pre-specified capability universe G of turn-based
tool-using agents, the three contracts may constitute a minimal generating set under an explicitly defined
implementation relation.

The empirical object is therefore architectural locality. If a new requirement can be implemented by
replacing or composing an existing component while leaving unrelated contracts and the execution kernel
unchanged, the change has low structural propagation. If the same requirement requires modifying shared
state representations, central runners, unrelated handlers, or several independent subsystems, the change
has higher propagation. This construct is closely related to established work on modularity and design
dependency structure, where dependency matrices are used to study how architectural structure affects
change and redesign. [5,6]

This manuscript is a revised research design and reference-implementation study. It does not present
unexecuted experiments as results. The supplied AgentCore source audit and research artifacts establish the
concrete implementation and motivate the protocol; they do not, by themselves, establish that AgentCore is
superior to other frameworks.


2. Research Questions and Contributions
RQ1 — Primitive sufficiency: For a pre-registered capability universe G describing turn-based, tool-using
agents, can every required capability be implemented using the primitive set {L, T, C}, where L is reasoning,
T is acting, and C is remembering, plus policies, composition, and contract-preserving layers?

RQ2 — Primitive necessity: Does removing any one primitive from the implementation basis cause at least
one capability in G to become unimplementable without either changing the remaining primitive contracts or
introducing a replacement primitive with equivalent semantic responsibility?

RQ3 — Architectural locality: Under matched requirement changes, does a primitive-first architecture reduce
the number and centrality of unrelated artifacts that must be changed, compared with alternative framework
architectures?

RQ4 — Fault locality: When a defect is injected into an isolated cross-cutting concern, does the primitive-first
architecture constrain functional impact and repair scope to the affected concern more often than alternative
architectures?

RQ5 — Human and AI implementation cost: When equivalent extension tasks are assigned to developers or
coding agents under controlled information conditions, does the architecture change implementation effort,
iteration count, or defect rate?

The contributions are therefore: (1) a falsifiable primitive-selection procedure; (2) a minimal-generating-set
formulation that distinguishes sufficiency from necessity; (3) architectural locality as the primary
comparative construct; (4) a matched-task empirical protocol; (5) a reference implementation in AgentCore;

3. Related Architectural Perspectives
Classical modular design argues for information hiding and decomposition around design decisions likely to
change. [7] The present work specializes that principle to agent runtimes by treating reasoning, acting, and
remembering as candidate semantic boundaries rather than treating planning, reflection, memory,
guardrails, or persistence as automatically separate architectural primitives.

Middleware and decorator architectures already provide contract-preserving extension mechanisms. The
novelty claimed here is not the mathematical observation that a wrapper F → F can compose with another
wrapper. That closure is routine. The research question is whether choosing a particular semantic primitive
basis changes the observed propagation of requirements and defects. The layer algebra is consequently
treated as an implementation mechanism and measurement aid, not as the main theoretical novelty.

Current agent frameworks demonstrate that several architectural representations are viable. OpenAI
documents agents as combinations of model instructions, tools, handoffs, guardrails, and runtime behavior.
Microsoft Agent Framework documents an agent pipeline containing middleware, context, and chat-client
layers and separately provides explicit graph workflows with executors, edges, events, and state. [1,2,3]
These systems are not treated as “bad” baselines; they are structurally different points in the design space
against which locality can be measured.

DeepSeek/Cordis provides a particularly important contrast. Cordis addresses dynamic composition by
formalizing reversible effects and reactive coeffects mediated through context, with explicit runtime support
for loading and reconciliation. [4] The present paper does not claim that primitive-first architecture
subsumes Cordis. Instead, it asks whether the more general composition machinery is required for the
narrower workload class studied here, and whether the two approaches can coexist at different architectural
levels.


4. Primitive-First Model
Let L, T, and C denote behavioral contracts for reasoning, acting, and remembering. An agent state is
represented abstractly as A = (L, T, C). The contracts are intentionally unopinionated: L determines how
model reasoning is requested and observed; T determines how available actions are discovered and invoked;
C determines how execution context is assembled, transformed, and persisted.

A layer over a contract F is written λF : F → F. A stack λ3 ∘ λ2 ∘ λ1 therefore remains an implementation of F.
This gives a convenient closure property: a concern that can be expressed entirely by wrapping one contract
does not require a new semantic primitive. Examples in the AgentCore evidence include retry around LLM
interaction, approval or discovery around tools, and persistence around context. The property is
architectural, not a claim that all concerns are single-axis.

The execution kernel can then be expressed as repeated interaction among the contracts: obtain model
output from L; if the output requests actions, dispatch through T; incorporate resulting events through C;
repeat until the termination condition is reached. The exact implementation may be asynchronous,
streaming, durable, or provider-specific. The model only requires that these responsibilities remain
contractually distinguishable.

The important methodological restriction is that the three contracts are not declared minimal merely
because the model was written using three names. Minimality is an empirical property. A primitive is
necessary only if removing it from the implementation basis prevents the target capability set from being
implemented without reintroducing an equivalent semantic boundary elsewhere.


5. Defining the Capability Universe Independently
The reviewer-critical change is that G must not be defined by inspecting AgentCore and then declaring
AgentCore sufficient. Before evaluating any architecture, the study freezes a capability matrix for the target
workload. The initial candidate matrix is derived from the common execution semantics of turn-based
tool-using agents and from documented capabilities across contemporary frameworks, rather than from
AgentCore's class names.

G0 — Model interaction: invoke a model with messages/instructions and receive a response or event stream.
G1 — Tool discovery: expose a set of executable actions to the model. G2 — Tool invocation: execute
selected actions and return results. G3 — Context continuity: carry conversation or working state across
turns. G4 — Termination: determine when an agent run is complete. G5 — Cross-cutting policy injection: add
concerns such as retry, validation, approval, logging, or rate limiting without changing the semantic task. G6
— Persistence/recovery: preserve enough execution state to resume after interruption. G7 — Composition:
combine agents or execution components into larger behavior. G8 — Human interruption/approval: suspend
or gate an action and resume later. G9 — Streaming/event observation: expose incremental or completed
execution events. G10 — Provider substitution: change the underlying model provider without changing the
application-level agent semantics.

This matrix is a starting protocol, not a result. Before the experiment, each capability must receive an
operational definition and at least one acceptance test. Capabilities that cannot be implemented by a given
framework without changing its intended programming model are recorded as out-of-scope rather than
silently normalized.

The study also records the implementation relation used for necessity. A capability is considered generated
by a basis if it can be implemented without adding a new semantic primitive category, while allowing
arbitrary ordinary code inside implementations and allowing composition/layers that preserve the declared
contracts. This prevents a superficial interface-count test from masquerading as a proof of minimality.


6. Necessity and Ablation
Sufficiency is evaluated by implementing every acceptance test in G using the candidate basis. Necessity
requires ablation. For each primitive P ∈ {L,T,C}, construct a constrained variant in which P is unavailable as
a first-class contract. The remaining contracts and the implementation language remain available. The
experiment then attempts to implement the same capability matrix.

The primary outcome is not whether the code becomes awkward. The primary outcome is whether a
capability becomes impossible under the constrained contract system. A secondary outcome records what
replacement structure is introduced. If removing C requires adding a new ContextStore primitive with
equivalent semantic responsibility, the result is evidence of replacement rather than evidence that the
original C was unnecessary. This distinction separates structural minimality from mere renaming.

A second ablation removes the layer mechanism while retaining the primitive contracts. This tests whether
the proposed locality effect depends on the existence of layers rather than on the primitive basis itself. A
third ablation retains layers but allows shared mutable state across primitives. This tests whether contract
preservation, rather than wrapper syntax, is responsible for observed fault locality.

The protocol therefore produces three separate claims: basis sufficiency, basis necessity, and
mechanism-level locality. They must not be collapsed into one theorem.


7. Experimental Protocol
The existing experiment design is retained but tightened around matched tasks and reproducibility. Five
experiments are planned.

Experiment 1 — Matched extensibility. Implement six concerns: retry, logging/telemetry, approval, caching,
rate limiting, and input validation. Each concern is implemented independently on every framework. Record
new files, modified files, core-runner modifications, public API changes, dependency-edge changes, and test
changes. A concern-removal pass then measures whether the implementation can be deleted without
unrelated edits.

Experiment 2 — Requirement evolution. Apply a pre-registered ten-phase sequence to the same baseline
agent: model substitution; additional tool; retry; approval; persistence; context compaction; telemetry;
human interruption; provider substitution; and multi-agent composition. Each phase is committed
separately. The primary measure is propagation: the number of artifacts outside the concern's natural
boundary that must change. Secondary measures include core-runner edits, dependency-edge additions,
and change amplification.

Experiment 3 — Architectural structure. Extract language-normalized structural metrics: public type count,
public method count, dependency edges, strongly connected components, coupling measures, abstraction
surface, and design-structure-matrix propagation cost. Raw LOC is reported descriptively but is not used as a
quality proxy. Established modularity research motivates dependency-structure analysis, while OO metrics
are treated cautiously because metric validity depends on the measurement context. [5,8,9]

Experiment 4 — AI-assisted implementation. Give coding agents the same task specifications and the same
capability documentation for every framework. Record input/output tokens, tool calls, compile/test cycles,
wall-clock time where measurable, first-pass success, final correctness, and defect count.
Framework-specific documentation is normalized to avoid rewarding a framework merely because the model
has seen more examples during pretraining. Each condition is repeated with fixed prompts and controlled
stochasticity where the model permits it.

Experiment 5 — Defect locality. Inject five realistic defects into isolated concerns: retry-counter failure,
approval argument loss, persistence deserialization failure, cache-key collision, and input-guardrail
exception. Run the full standardized test harness. Record unrelated failing tests, number of files required for
repair, whether the execution kernel is edited, and dependency changes. The existing research protocol
already defines F_affected, L_leak, F_fix, and C_fix for this purpose.

The primary statistical analysis uses paired non-parametric comparisons for matched tasks and reports
effect sizes with confidence intervals. Multiple comparisons are corrected. No statistical test is interpreted as
evidence of architectural superiority unless the task, implementation conditions, and measurement
procedure are held constant.


8. Architectural Locality Metrics
The principal dependent construct is propagation rather than code size. For a change request r, let M(r) be
the set of modified artifacts and B(r) the set of artifacts belonging to the natural implementation boundary of
r. Define external propagation as P_ext(r) = |M(r) − B(r)|. A normalized form is I_ext(r) = |M(r) − B(r)| /
max(1, |M(r)|).

A dependency-aware version weights modifications by their graph distance from the target boundary. Let
d(v,B) be the shortest dependency distance from artifact v to the natural boundary B. The propagation radius
is R_p(r) = max d(v,B) over modified artifacts. The protocol also records whether a central execution artifact
is touched, because a single change to a highly connected runner can have greater architectural significance
than several isolated file edits.

For fault injection, locality is measured separately from change propagation. Let L_leak be a binary indicator
that a defect in one concern causes an observable failure in an unrelated concern. Let F_fix be the number of
distinct artifacts changed to repair the defect and C_fix indicate whether the central execution kernel was
modified.

These measures do not assert that smaller propagation is always better. A workflow engine may intentionally
propagate a requirement through a graph because the requirement changes execution topology. The study
therefore reports whether the observed propagation matches the declared responsibility of the requirement,
rather than treating all cross-component changes as defects.


9. AgentCore as Reference Implementation
AgentCore is the treatment implementation used to make the architectural hypothesis concrete. The
supplied source artifacts identify ILLM, IToolbox, and IContext as the principal contracts, with context
assembly/normalization/summarization/truncation components and optional layers for retry, guardrails,
tool-call handling, approval, discovery, and chat persistence. The supplied ChatPersistenceLayer is
particularly relevant because it wraps IContext, restores state from a store/WAL, forwards context events,
persists new messages, and clears the WAL after successful persistence.

The supplied evidence reports approximately 2,848 lines across 46 framework files in one audited snapshot,
with a small core execution loop and separate layer/provider/MCP components. A different project-structure
snapshot in the supplied materials reports different totals. The revised manuscript therefore treats exact line
counts as snapshot-specific and requires commit hashes plus an automated counting script before
publication. No cross-framework LOC ranking is used as an inferential result.

10. Reproducibility and Artifact Protocol
Every evaluated framework must be pinned to an immutable commit or release. The artifact bundle must
contain: repository URL; commit hash; checkout date; language/runtime version; build instructions; exact
feature configuration; task specifications; acceptance tests; architecture-classification rubric; metric
extraction scripts; raw measurement files; analysis notebooks/scripts; and generated tables.

The classification rubric is released before the final comparison. For every changed file, the evaluator records
its role, the requirement phase that caused the change, whether the file is inside the natural boundary,
whether the change touches a public contract, and whether the change introduces a new semantic
abstraction. Disagreements are adjudicated using the pre-registered rubric and reported rather than silently
resolved.

The study must also distinguish framework code from examples, tests, generated files, vendored
dependencies, integrations, and applications. Any LOC or type-count table therefore reports the exact
inclusion rule. The earlier broad table spanning frameworks and production agents is retained only as a
descriptive survey, not as an apples-to-apples architectural comparison.

The public artifact should be versioned independently of the manuscript and archived with a persistent
identifier. The reviewer's criticism that private [A1]–[A9] artifacts are not independently inspectable is
accepted as a publication blocker, not as a minor formatting issue.


11. Counterexamples and Boundary Conditions
Primitive-first architecture is not asserted to be universally sufficient. The supplied counterexample analysis
identifies several important boundaries.

First, some operations are inherently multi-primitive transactions. A capability that must atomically update
model state, tool state, and persistent context may require an explicit transaction coordinator or
workflow-level abstraction. Forcing such a capability into one primitive would hide rather than remove
coupling.

Second, layer ordering can be semantically significant. Retry followed by caching is not generally equivalent
to caching followed by retry. Therefore the endomorphism composition is associative as an operation on a
chosen stack, but different orderings may have different behavior. The algebra does not eliminate policy
interaction.

Third, substrate leakage can violate contract isolation. A layer that depends on a shared database, ambient
process state, global event bus, or provider-specific mutable state may create dependencies outside its
apparent interface. The type signature F → F is therefore insufficient to guarantee operational isolation.

Fourth, AI-facing semantics may require richer contracts. If an agent must reason explicitly over workflow
topology, temporal commitments, or multi-agent negotiation, a three-axis model may cease to be an
adequate abstraction. Such cases should be recorded as capability-universe violations rather than forced
into the model.

These boundaries are part of the falsification strategy. A negative result is scientifically useful: it identifies
the class of requirements for which the primitive basis ceases to be sufficient.


12. What the Current Evidence Establishes
The supplied materials establish a coherent reference implementation, a formal vocabulary, a set of
architectural hypotheses, a counterexample taxonomy, and a detailed experimental protocol. They also
establish that several concerns can be implemented as layers around the current AgentCore contracts
without editing the small execution kernel in the supplied snapshot.

They do not establish that AgentCore has lower maintenance cost, lower developer cognitive load, lower
defect rate, or lower AI implementation cost than competing frameworks. They do not establish that three



                                  Primitive-First Architecture — Revised Manuscript v2 — 6
primitives are mathematically minimal for all agents. They do not establish causal superiority from LOC
differences. Those claims require the controlled experiments specified here.

This separation is deliberate. A publishable empirical result should survive an outcome in which the
primitive-first hypothesis is only partially supported. For example, it may reduce propagation for
cross-cutting concerns while performing no better for workflow-topology changes. The protocol is designed to
reveal that boundary rather than conceal it.


13. Conclusion
Primitive-first architecture is best understood as a falsifiable hypothesis about architectural representation.
The proposed representation separates stable semantic contracts from policies, composition, and
contract-preserving layers. The research contribution is not the observation that decorators compose, nor
the observation that one implementation is small. It is the proposed method for selecting and testing a
primitive basis and the hypothesis that this choice affects architectural locality under change and fault.

The revised protocol makes the central claims independently testable. A capability universe is frozen before
evaluation. Sufficiency and necessity are separated. Primitive ablations test necessity. Matched requirement
evolution measures propagation. Fault injection tests locality. AI-assisted implementation measures whether
the architectural representation changes the cost of generating and repairing code. Structural metrics
provide supporting evidence rather than serving as substitutes for behavioral experiments.

AgentCore provides a concrete implementation through which the hypotheses can be exercised, but the
theory must survive outside that implementation. The decisive next step is therefore not another
architectural argument. It is execution of the preregistered experiments across pinned baselines, release of
the raw artifacts, and independent replication.
