  Primitive-First Architecture for LLM Agent Systems:
    Decomposition, Compositional Extensibility, and
Architectural Complexity under AI-Assisted Development
      A design-science and source-level comparative study using AgentCore as a reference implementation

                       Anonymous Author • September 2026 • Research Manuscript / Preprint Draft

Abstract
Large language models have made software generation dramatically cheaper, changing the economics of architectural
abstraction. This paper investigates whether that change creates a new need for architectural discipline: instead of
allowing every new requirement to generate another interface, registry, executor, manager, hook, or workflow abstraction,
can an agent system be organized around a small set of stable semantic primitives, with variability expressed through
injectable policies, composition, and type-preserving layers? We call this approach primitive-first architecture. We
formalize the approach for turn-based, tool-using LLM agents as three behavioral contracts—reasoning (ILLM), acting
(IToolbox), and remembering (IContext)—and model a layer as an endomorphism λ:F→F over one primitive. The paper
deliberately does not claim that three primitives are universally necessary or that layers solve every architectural problem.
Instead, it treats the three-axis model as a testable architectural basis for the class of agents studied and identifies explicit
boundary conditions where it can fail. The empirical component is a source-level audit of AgentCore and a comparative
corpus assembled by the authors across 22 agent frameworks and production agents. The supplied audit reports
approximately 2,848 lines of framework code for AgentCore, compared with 3,302–1,070,131 lines across the other
measured systems; this is reported as descriptive evidence only because scope, language, feature breadth, and maturity
differ. AgentCore's reference implementation contains an approximately 18-line core execution loop and demonstrates
retries, guardrails, tool approval/discovery, persistence, and other extensions as policies or layers without modifying that
loop. The study also contrasts the approach with LangGraph's actor/channel Pregel model, Microsoft Agent Framework's
production orchestration and middleware, Pydantic AI's capability-oriented architecture, and DeepSeek Harness/Cordis's
everything-is-a-plugin context paradigm. The resulting contribution is a research framework rather than a claim of
universal superiority: (1) a precise vocabulary separating primitives, policies, composition, and layers; (2) a formal model
for primitive-preserving extension; (3) an operational complexity battery centered on propagation cost, API surface,
abstraction inventory, change amplification, and AI context footprint; (4) a reproducible source-audit methodology; and (5)
a falsification program identifying multi-primitive transactions, layer-order dependence, substrate leakage, and AI-facing
semantic insufficiency as critical failure modes. The controlled experiments required to establish causal superiority
remain future work; no unexecuted statistical result is presented as an observed finding.
Keywords: LLM agents; agent harnesses; software architecture; architectural complexity; primitive decomposition; modularity; decorators;
middleware; composability; AI-assisted software engineering; technical debt

1. Introduction
The software-engineering problem addressed here is not that contemporary agent frameworks are incapable. They are
capable precisely because they have accumulated mechanisms for routing, state, tool execution, observability, durability,
human approval, multi-agent coordination, provider compatibility, and deployment. The research question is whether the
accumulation of mechanisms should also determine the architectural ontology of the system.

Classical software-engineering work has long argued that the criteria used to decompose a system determine its flexibility
and comprehensibility. Parnas showed that alternative decompositions of the same system can have materially different
maintenance properties [1]. Brooks distinguished essential difficulty from accidental difficulty [2], while Moseley and
Marks later argued that state and control-flow complexity are major sources of accidental complexity [3]. Ousterhout's
more recent treatment of modular design emphasizes that an abstraction is valuable when a relatively small interface
hides substantial implementation complexity; a proliferation of shallow modules can increase rather than reduce system
complexity [4].

The rise of AI-assisted programming changes the cost structure surrounding these principles. Code generation systems
can cheaply produce another wrapper, interface, factory, callback, registry, or adapter. Recent empirical and
observational studies report quality and maintainability concerns in generated code, including distinctive bug patterns [5],
maintainability problems in generated patches [6], code-churn and reuse concerns in large change datasets [7], and
self-admitted technical debt associated with generative-AI use [8]. These findings do not establish that AI necessarily
produces worse software; they establish that correctness and maintainability cannot be assumed to improve merely
because code production becomes cheaper.

This paper therefore investigates a design hypothesis: architectural complexity should be constrained at the level of
decomposition, before extensions are added. The proposed response is primitive-first architecture: identify domain
primitives that directly express the stable semantics of the problem; keep variation that is internal to a primitive as
injectable policy; and express cross-cutting behavior, where semantically valid, as layers that preserve the primitive's
contract.

The central research question is:
RQ1. For turn-based, tool-using LLM agents, does a primitive-first decomposition provide a stable architectural basis that
permits common extensions with lower architectural disturbance than graph-, plugin-, hook-, or capability-heavy
alternatives?

Secondary questions are:
RQ2. Which dimensions of architectural complexity are most appropriate for evaluating such a claim?
RQ3. Which extension classes can be represented as type-preserving layers, and which necessarily require richer
coordination abstractions?
RQ4. Does the architecture remain useful when software is generated and evolved by AI coding agents, or does
minimality reduce the semantic structure those agents need?

The paper's position is deliberately narrower than the strongest claims in the preliminary AgentCore research notes. We
do not attempt to prove that every agent is exactly three interfaces, that all alternative architectures are redundant, or that
fewer lines of code imply better architecture. Instead, we formulate a model that can be empirically rejected.

2. Background and Related Work
2.1 Decomposition and information hiding. Parnas's classic work makes decomposition criteria a first-class design
decision: modules should hide design decisions likely to change, rather than merely partition implementation by
procedural convenience [1]. This provides a direct theoretical predecessor for primitive-first design. The present work
differs in attempting to identify a domain-level basis for LLM agents and then constrain extension mechanisms around
that basis.

2.2 Essential and accidental complexity. Brooks's distinction between essential and accidental difficulty motivates the
idea that architectural machinery should not be mistaken for domain complexity [2]. Moseley and Marks similarly
emphasize state, explicit control flow, and code volume as sources of complexity that can sometimes be reduced by
changing representation [3]. The present work treats abstraction proliferation as one candidate form of accidental
architectural complexity, while recognizing that some complexity is unavoidable.

2.3 Deep versus shallow modules. Ousterhout argues that a module's interface is a complexity cost and that deep
modules can hide substantial implementation complexity behind a small contract [4]. This is closely related to the present

claim that an interface should be semantically complete enough that new requirements can often be expressed through
the existing boundary. Importantly, primitive-first architecture is therefore not “small class first.” It can produce a large
implementation behind a stable interface.

2.4 ReAct and agent execution. ReAct established a simple loop in which language-model reasoning and external
action are interleaved [9]. This is the behavioral starting point for AgentCore. Modern agent harnesses add state
persistence, tool mediation, context management, provider adaptation, guardrails, and orchestration around that loop.
The question here is whether those additions should become new architectural primitives or remain composition around a
stable execution basis.

2.5 Contemporary agent-harness architectures. LangGraph uses an actor/channel model organized around
Pregel-style plan, execution, and update phases [10]. Microsoft Agent Framework explicitly targets production agents and
multi-agent workflows, with graph-based patterns, durability, observability, governance, human-in-the-loop control, and
middleware [11]. Pydantic AI currently presents a composable capabilities system in which reusable capabilities bundle
tools, instructions, hooks, and model settings [12]. OpenAI's Agents SDK emphasizes a deliberately small set of
primitives—agents, agents-as-tools/handoffs, and guardrails—while also providing tracing and evaluation facilities [13].
These systems demonstrate that the industry is already experimenting with different answers to the “what is an agent?”
question.

2.6 DeepSeek Harness and Cordis. The most direct contemporary theoretical comparison is Shi, Zhang, and Cui's 2026
“A Programming Paradigm for Spatiotemporal Composability.” The paper formalizes temporal composability through
revertible effects and spatial composability through reactive coeffects, and implements the ideas in Cordis [14].
DeepSeek Harness applies this model with an explicit “everything is a plugin” architecture: the model adapter, tool
registry, session log, and agent loop are all plugins mounted into a shared context [15]. The present work asks a different
question. Cordis studies how arbitrary components can be composed and safely reconfigured at runtime; primitive-first
architecture studies whether the set of components exposed as first-class architectural entities can itself be made smaller
and more semantically stable.

A recent 2026 source-level study of three coding-agent harnesses—deepagents, pi, and DeepSeek dsh—also reports
architectural convergence around a commoditized loop, replayable session state, model-specific data, progressive
context disclosure, and explicit extension seams [16]. This strengthens the motivation for studying the harness as an
architectural object rather than treating the LLM as the entire agent. It also provides an important caution: convergence
does not imply that one decomposition is uniquely correct.

3. Primitive-First Architecture
3.1 Definition. A primitive is defined here as a domain-level contract that directly represents a stable semantic capability
required by the target execution model. A primitive is not merely a class with few methods, and it is not “primitive”
because its implementation is small. The criterion is semantic: removing the boundary must either collapse distinct
responsibilities into one contract or force clients to reconstruct the missing capability repeatedly.

A policy is a replaceable decision or strategy internal to a primitive's responsibility. Examples in AgentCore include
message assembly, normalization, token estimation, truncation, and compaction. A composition combines primitives or
policies to form a higher-level behavior without changing their contracts. A layer is a contract-preserving wrapper, formally
an endomorphism λ:F→F over an existing primitive F.

The four concepts are therefore:
Primitive: what the system fundamentally does.
Policy: how a primitive chooses to do something within its semantic boundary.
Composition: how existing capabilities are combined into a larger behavior.
Layer: how behavior is intercepted or augmented while preserving a capability's contract.

This separation is the core conceptual contribution. It replaces an undifferentiated notion of “extensibility” with distinct
mechanisms whose use can be evaluated.

3.2 The Agent Triple. For the target class of turn-based, tool-using agents, AgentCore uses three behavioral contracts:
L = reasoning: generate message events from message history, tool definitions, and optional response constraints.
T = acting: register and execute tools, producing result events.
C = remembering: ingest events, assemble completed messages, maintain history, and expose the working context.
Thus:
A = (L, T, C).
The supplied architecture analysis documents the contracts as ILLM, IToolbox, and IContext. The implementation
deliberately keeps ILLM independent of context and tools; IToolbox independent of the LLM and context; and IContext

independent of the LLM and tools [A1].

3.3 Why these three are useful. The three contracts correspond directly to the execution dependencies of a
conventional ReAct-style agent: the model needs a context and tool definitions; a tool call produces an external side
effect; and both model outputs and tool results must become part of the subsequent context. This makes the triple a
useful basis for the studied class of systems.

The important qualification is that this is not a proof that no fourth primitive can ever exist. A distributed transactional
coordinator, a real-time media transport, or a provenance-verification subsystem can introduce semantics that do not fit
cleanly inside a single member of the triple. The stronger universal claim is therefore rejected in favor of a bounded claim:
the triple is a sufficient basis for the single-agent, turn-oriented execution model implemented and studied here.

3.4 The execution fixed point. The core loop can be written as:
x■ = C.write(user)
(m■, T■) = C.write(L(C.read(), Defs(T)))
if T■ ≠ ∅, then C.write(T(T■)) and continue; otherwise terminate.
With a finite maximum iteration bound Kmax, the implementation terminates when no tool calls remain or the bound is
reached. This is not a new agent algorithm; it is an explicit architectural expression of the ReAct execution pattern [9].

4. Extensibility as Contract-Preserving Layers
For a primitive F, a layer λ is a function:
λ : F → F.
A layer receives an implementation of F and returns another implementation satisfying the same public contract.
Composition therefore forms the usual endomorphism monoid:
(End(F), ■, id).
Closure follows because composing two contract-preserving wrappers yields another implementation of F. Associativity
follows from function composition, and the identity element is the pass-through layer. This algebra is elementary; the
research contribution is not inventing decorators or monoids. The contribution is applying the distinction systematically to
agent architecture and asking whether it reduces architectural disturbance.

AgentCore currently demonstrates layers for LLM retry and input guardrails, tool approval and discovery, and context
persistence [A1]. The project structure also separates policies such as assembler, normalizer, tokenizer, summarizer,
and truncator from the three top-level contracts [A2]. The persistence implementation wraps context rather than teaching
the agent loop about storage: streaming events can be written through a WAL before reaching the underlying context,
and recovered history can be restored through the same context boundary [A3].

The model gives a concrete rule:
If a new concern can be expressed as a transformation of one existing capability while preserving that
capability's contract, it should be a layer rather than a new core primitive.

This rule is stronger than “use decorators.” It tells an architect when the mechanism is appropriate. It also predicts failure:
if a requirement cannot preserve one primitive's contract, forcing it into a layer is likely to create hidden state, ordering
hazards, or cross-boundary leakage.

Layer order is therefore part of the semantics. In general:
λ■ ■ λ■ ≠ λ■ ■ λ■.
For example, retrying an operation before validation is not necessarily equivalent to validating before retrying. This means
that a layer stack is not automatically simpler merely because every layer has a small implementation. Primitive-first
architecture therefore treats layer ordering as a known complexity dimension, not an ignored implementation detail.

5. Formal Research Model
The preliminary AgentCore notes proposed a “decomposition theorem” asserting that every autonomous agent
decomposes into exactly three interfaces. We refine that claim for scientific defensibility.

Definition 1 (Target agent class). Let G be the class of agents whose execution consists of repeated cycles of: (i)
constructing a message/tool input, (ii) invoking a reasoning model, (iii) executing explicitly represented tool calls, and (iv)
incorporating resulting events into an ordered working context.

Proposition 1 (Three-axis sufficiency for G). Every execution trace in G can be represented using a reasoning contract
L, an acting contract T, and a remembering contract C, together with composition and policies internal to those contracts.

The proposition is constructive rather than universal. A trace is generated by repeatedly applying L to C's current history
and T's available definitions; tool calls are interpreted by T and their results are written to C. Therefore no additional


Primitive-First Architecture for LLM Agent Systems — Research Manuscript                                                      4
architectural primitive is required to reproduce the execution semantics of G.

Proposition 2 (Layer closure). If λ■:F→F and λ■:F→F preserve the contract of primitive F, then λ■■λ■:F→F is also a
valid layer. Consequently, arbitrary finite stacks of contract-preserving layers can extend F without changing the type of
the capability consumed by the agent.

Proposition 3 (Local extension). If a requirement r can be expressed entirely as λ:F→F for one primitive F, then
implementing r does not require modifying the agent execution function, assuming the agent depends only on F's
contract.

These propositions are modest but falsifiable. Proposition 1 fails for the target class if a required execution semantic
cannot be represented by L, T, C without an additional independent state machine. Proposition 3 fails when a concern
necessarily coordinates two or more primitives. The framework therefore does not define “correctness” as “whatever can
be forced into the triple.”

Architectural disturbance. To compare designs, define the disturbance of requirement r as a vector:
D(r) = ■F_mod, A_mod, I_mod, Dep_mod, Core_mod■,
where F_mod is the number of existing files/components modified, A_mod the number of architectural abstractions added
or modified, I_mod the number of public contracts changed, Dep_mod the number of dependency relationships altered,
and Core_mod an indicator that the execution kernel changed. This vector should be reported rather than collapsed
prematurely into one arbitrary score.

The research hypothesis is then:
H1. For extension tasks that are semantically single-axis, primitive-first designs will exhibit lower architectural disturbance
than alternative designs.
H2. For requirement sequences drawn from the same target capability set, primitive-first designs will exhibit lower
cumulative change amplification.
H3. The advantage, if any, will disappear or reverse for requirements that inherently coordinate multiple primitives or
require substrate-specific semantics.
H4. Under AI-assisted implementation, a stable primitive basis will reduce the number of architectural concepts an agent
must discover before making local changes, provided that the primitive contracts remain semantically rich enough.

These hypotheses are intentionally not universal superiority claims.

6. Research Method
The research combines design science, source-level comparative analysis, and a pre-registered-style experimental
protocol. The first two components are supported by the current artifact set; the controlled experiments are specified but
not yet executed in the supplied evidence.

6.1 Source corpus. The supplied evidence file reports a source audit spanning 22 frameworks and production agents,
including AgentCore, atomic-agents, Claude Agent SDK, smolagents, LangGraph, OpenAI Agents SDK, Haystack,
LangChain Core, DSPy, Microsoft Agent Framework, Pydantic AI, Letta, Google ADK, DeerFlow, aider, claw-code,
OpenHands, opencode, Cline, DeepSeek Harness, Codex, and Qwen Code [A5]. The audit excluded
tests/examples/docs from the reported framework line counts. Because repositories differ in language, scope, maturity,
and functionality, these counts are treated as descriptive size indicators rather than evidence of quality.

6.2 Architecture coding scheme. Each system is classified along seven dimensions: core primitives, execution model,
extension mechanism, context/memory, tools, persistence/recovery, and notable architectural mechanisms. The survey
distinguishes foundational orchestration frameworks from vendor-specific SDKs and specialized systems [A6].

6.3 Complexity measurement. The proposed Multi-Dimensional Framework Complexity Battery (MFCB) combines: (1)
structural size and abstraction inventory; (2) architectural coupling and propagation cost; (3) API/cognitive surface; and
(4) AI context and implementation footprint [A4]. This follows the empirical lesson that no single software metric captures
architectural complexity. Cai et al.'s ICSE 2025 study of more than 1,200 C++ and Java projects found statistically
significant relationships between architectural complexity measures such as propagation cost and maintenance activity
[17].

The primary measures proposed for future controlled comparison are:
• Propagation Cost (PC): the proportion of architectural elements affected by a change, using a dependency-graph/DSM
formulation.
• Change Amplification (CA): number of pre-existing components/contracts that must be modified to implement a
requirement.
• Abstraction Inventory (AIv): counts of public types, interfaces, registries, factories, executors, and orchestration
nodes, normalized by delivered capability.

Primitive-First Architecture for LLM Agent Systems — Research Manuscript                                                      5
• API Surface Area (ASA): a vector describing public types, methods, parameters, properties, and configuration
concepts exposed to a client.
• Conceptual Load (CL): number of distinct concepts a developer must understand to implement a standardized task,
measured through controlled task studies rather than a hard-coded psychological threshold.
• AI Context Footprint (CIF): tokens of repository/context material an AI coding agent must ingest before it can safely
perform a specified task.
• Implementation Trajectory Cost (ITC): input/output tokens, tool calls, compile-test cycles, and wall-clock time required
by an AI coding agent to implement a task successfully.

Raw LOC remains useful as a secondary descriptive measure but is explicitly not used as a proxy for architectural quality.
The current AgentCore audit illustrates why: its framework is substantially smaller than the measured baselines, but this
may partly reflect narrower scope and a deliberately minimal feature set [A5].

7. AgentCore Reference Implementation
AgentCore is treated as a reference implementation, not as proof by existence. The supplied architecture analysis reports
three top-level behavioral contracts: ILLM, IToolbox, and IContext [A1]. The agent loop consumes those contracts and
has remained stable through the architecture's reported evolution.

The project structure separates the core from extension packages. Context contains primitives such as assembler,
normalizer, summarizer, tokenizer, and truncator; LLM contains the LLM contract and layer base; Tool contains the
toolbox and tool representation; and a separate Layers project contains retry, guardrail, tool-call detection, approval,
discovery, and persistence layers [A2]. This is a concrete example of the primitive/policy/layer distinction.

The supplied evidence audit reports approximately 2,848 framework lines across 46 files, including the core, layers,
multi-agent package, provider adapter, and MCP package [A5]. The same audit reports 3,302 lines for atomic-agents;
10,313 for Claude Agent SDK; 10,998 for smolagents; 16,201 for LangGraph; 41,638 for OpenAI Agents SDK; 111,489
for Microsoft Agent Framework; 113,851 for Pydantic AI; 145,336 for Google ADK; and 168,950 for DeerFlow. It also
reports substantially larger production-agent codebases, including 298,219 lines for DeepSeek Harness and 1,070,131
for Qwen Code. These figures are retained because they are reproducible measurements in the supplied artifact, but they
are not treated as normalized complexity scores.

The more informative evidence is architectural locality. AgentCore demonstrates that retry can be placed around ILLM,
approval and discovery around IToolbox, and persistence around IContext without changing the execution kernel [A1].
This directly instantiates Proposition 3 for those concerns.

The implementation also exposes important limitations. The supplied counterexample analysis identifies
non-commutative layer stacks, multi-primitive transactions, substrate leakage, and the possibility that AI agents perform
better when given rich semantic abstractions rather than minimal low-level primitives [A7]. These limitations are
incorporated into the research model rather than hidden.

8. Comparative Analysis
8.1 LangGraph. LangGraph's Pregel runtime explicitly combines actors and channels and organizes execution into plan,
execution, and update phases [10]. This is appropriate when the system's problem is general graph execution,
synchronization, state channels, and conditional workflows. Primitive-first architecture does not argue that graphs are
unnecessary in general. It argues that a fixed graph engine is not required to express the basic single-agent ReAct loop
represented by L, T, and C. The research question is whether the additional graph machinery is justified for the target
workload.

8.2 Microsoft Agent Framework. Microsoft Agent Framework targets production-grade agents and multi-agent
workflows, including sequential, concurrent, handoff, and group collaboration patterns, as well as durability, observability,
governance, human-in-the-loop control, provider flexibility, and middleware [11]. These are deliberately broader
requirements than the minimal single-agent target. Therefore MAF is a valuable baseline for architectural richness, but
direct LOC comparison risks comparing different product scopes.

8.3 Pydantic AI. Pydantic AI currently describes a capability model in which reusable capabilities bundle tools,
instructions, hooks, and model settings, while its harness provides additional functionality such as code execution, file
access, guardrails, and sub-agent orchestration [12]. This is particularly relevant because it is itself an attempt to balance
composability and a small conceptual surface. Any empirical study should therefore compare task-level architectural
disturbance rather than assume that “more classes” equals “more complexity.”

8.4 OpenAI Agents SDK. OpenAI explicitly describes its SDK as using a small set of primitives—agents,
agents-as-tools/handoffs, and guardrails [13]. This is an important counterpoint to the claim that contemporary
frameworks universally suffer from excessive primitive proliferation. The paper therefore does not position primitive-first
architecture as synonymous with “fewest primitives”; instead, it investigates the criterion by which primitives are chosen
and extended.

8.5 DeepSeek Harness/Cordis. DeepSeek Harness takes the opposite architectural stance: every part of the product is
a plugin, including the model adapter, tool registry, session log, and agent loop, with a shared context mediating services,
typed events, and reversible effects [15]. Cordis provides formal machinery for safe dynamic composition [14].
Primitive-first architecture does not dispute the value of that machinery. The proposed comparison is between two levels
of design: composition mechanics versus primitive selection. A plugin architecture answers “how can arbitrary
components be replaced and recomposed?” Primitive-first architecture asks “which things should be first-class
components in the first place?”

8.6 Architectural convergence. The 2026 study of deepagents, pi, and dsh is especially relevant because it finds
convergence around a small set of harness elements despite very different starting philosophies [16]. This suggests that
the research problem is timely: mature agents appear to rediscover a relatively small set of durable concepts.
Primitive-first architecture can be evaluated as a hypothesis about why such convergence occurs and whether it can be
made explicit earlier in the design process.

9. Results of the Current Source-Level Study
The current artifact supports three categories of result.

Result 1: A compact behavioral basis is implementable. AgentCore implements the target turn-based agent
execution model through ILLM, IToolbox, and IContext, with an execution kernel reported as approximately 18 lines of
core logic [A1, A8]. This demonstrates sufficiency for the selected workload; it does not prove necessity.

Result 2: Several common extensions are locally expressible. The supplied implementation contains retry, input
guardrails, tool approval, tool discovery, tool-call detection, and context persistence as layers over one of the three
contracts [A1]. The persistence layer demonstrates a particularly concrete separation: streaming events are passed
through the context layer while storage and recovery remain outside the agent loop [A3].

Result 3: The architecture has identifiable failure boundaries. The adversarial analysis shows that layer order can
matter, multi-primitive transactions can require coordination, physical/runtime constraints can leak through abstractions,
and AI agents may require richer semantic interfaces to operate reliably [A7]. These are not incidental caveats; they
define the conditions under which the paradigm should be expected to lose its advantage.

The source audit also shows that AgentCore is physically smaller than the measured comparison corpus [A5]. The
appropriate conclusion is not “AgentCore is proven simpler.” The defensible conclusion is: AgentCore provides a compact
testbed in which the primitive-first decomposition is observable and several extensions are implemented without changing
the core loop.

10. Adversarial Analysis and Falsification
A credible architectural theory must specify how it can lose.

F1 — Primitive insufficiency. If a required capability repeatedly forces consumer code to reconstruct missing domain
semantics, the chosen primitive is too weak. A minimal primitive that merely pushes complexity outward is not a
successful abstraction.

F2 — Cross-primitive entanglement. If a requirement must atomically coordinate L, T, and C—such as transactional
rollback of a tool side effect together with context rewind and prompt-routing changes—then a single-axis layer cannot
express the requirement without a mediator. Such a result would establish a genuine boundary for the three-axis model.

F3 — Layer-order explosion. If N layers create a large set of semantically valid/invalid permutations and developers
must reason about those permutations to use the framework safely, the layer mechanism may merely relocate
complexity. This is the software equivalent of middleware or interceptor “hell.”

F4 — AI semantic insufficiency. If controlled coding-agent experiments show that richer, specialized abstractions
reduce implementation errors and agent trajectories relative to the minimal primitive model, then primitive minimality is
counterproductive for AI consumers. The research would then need to distinguish human-facing architectural simplicity
from machine-facing semantic scaffolding.

F5 — Scope mismatch. If a competing framework's extra machinery is required for capabilities intentionally excluded
from the AgentCore target, lower size or disturbance in AgentCore cannot be interpreted as a fair superiority claim. This is
why future experiments must compare standardized task slices, not entire products indiscriminately.

These failure conditions convert the original intuition—“correct code naturally becomes minimal”—into a falsifiable
proposition: minimality is beneficial only when the selected primitive retains the essential semantics required by the target
workload.

11. Experimental Program
The supplied experiment-design artifact specifies five experiments [A9]. We preserve that program but distinguish
planned experiments from executed evidence.

Experiment 1: Extensibility cost. Implement retry, logging, approval, caching, rate limiting, and validation under each
architecture. Measure new files, modified files, changed public contracts, core-loop modifications, and removability. The
paired nature of the tasks supports non-parametric comparison such as Wilcoxon signed-rank testing.

Experiment 2: Requirement evolution. Start from a minimal agent and apply a fixed sequence of requirements. At each
step record changed components, new abstractions, dependency changes, and whether the core loop changes. The
primary outcome is cumulative architectural disturbance rather than raw LOC.

Experiment 3: Abstraction and conceptual surface. Count public types, interfaces, methods, configuration concepts,
and dependency edges. Supplement static measures with controlled developer or coding-agent tasks so that conceptual
load is not inferred from type counts alone.

Experiment 4: AI implementation cost. Give equivalent repository tasks to coding agents under matched context
budgets. Measure input/output tokens, tool calls, compile-test cycles, successful completion, defects, and architectural
changes. This experiment is the direct test of the AI-era motivation.

Experiment 5: Defect locality. Inject equivalent defects into each architecture and measure the number of components
touched by diagnosis and repair. A primitive-first design predicts that single-axis concerns will have a smaller fault radius,
but cross-axis defects are expected to weaken that advantage.

The planned statistical protocol in the supplied methodology uses conservative non-parametric tests, effect sizes, and
explicit validity controls [A9]. However, none of these tests should be reported as completed until the experiments have
actually been run. This manuscript therefore reports the protocol, not invented p-values or effect sizes.

12. Threats to Validity
Construct validity. “Complexity” is multidimensional. LOC, type counts, and interface counts can be misleading. The
study therefore uses a vector of architectural and task-level measures.

Internal validity. AgentCore is authored by the researcher who proposes the paradigm. That creates a strong
author-optimization threat. Future comparative implementations should be performed from standardized task
specifications, ideally by independent engineers or blind coding agents, with equivalent feature requirements.

External validity. The three-axis model is derived from turn-based tool-using agents. It should not be assumed to cover
realtime voice, distributed workflow engines, embedded control, or arbitrary software systems without additional study.

Language and scope confounding. The source corpus mixes C#, Python, TypeScript, and Rust. Raw line counts are
therefore descriptive and should not be used as normalized evidence of quality. A fair benchmark should compare
standardized capability slices or use language-aware structural measures.

Framework maturity. Large frameworks often include capabilities that AgentCore intentionally omits. Comparing entire
repository size therefore rewards narrower scope. The correct unit of comparison is a common task plus the architecture
required to implement it.

Researcher degrees of freedom. Choosing primitives after observing implementation results risks circularity. The
primitive validity criteria should therefore be frozen before the main benchmark, and counterexamples should be included
rather than excluded.

AI evaluation leakage. Coding models may have seen public framework repositories during training. Future experiments
should provide matched documentation, record model/version/date, control tool availability, and run multiple independent
trials.

13. Discussion

Primitive-First Architecture for LLM Agent Systems — Research Manuscript                                                     8
The central insight supported by the current evidence is narrower and more useful than the slogan “less code is better.”
Software architecture should not optimize for line count. It should optimize for semantic compression: how much behavior
and domain complexity can be represented behind stable contracts without forcing clients to reconstruct hidden
semantics.

Primitive-first architecture is a proposed way to make that goal explicit. It asks the architect to identify the smallest set of
domain contracts that are genuinely semantically complete, then resist turning every new requirement into a new
architectural noun. Variation inside a primitive becomes policy. Combination becomes composition. Contract-preserving
cross-cutting behavior becomes a layer. A new primitive is introduced only when the requirement represents a genuinely
independent semantic capability.

This gives a more precise interpretation of the user's original observation that “correct code naturally becomes minimal.”
The claim is not that correctness mathematically implies fewer lines. The claim is that when decomposition boundaries
align with stable domain semantics, many later abstractions become unnecessary. The reduction in code is then an
outcome of a better representation, not the optimization target.

This also explains why the idea is particularly relevant to AI-assisted development. An LLM can easily produce a locally
reasonable abstraction. The marginal cost of another wrapper is tiny. The difficult problem becomes preventing locally
plausible abstractions from accumulating into a globally fragmented ontology. A primitive-first rule supplies a
search-space constraint for the coding agent: before inventing a new abstraction, attempt to express the requirement
using an existing primitive, policy, composition, or layer. The rule is architectural, not stylistic.

DeepSeek/Cordis makes an illuminating contrast. Cordis provides powerful machinery for arbitrary plugin composition,
including dynamic activation and reversible effects [14,15]. Primitive-first architecture instead reduces the number of
places where arbitrary composition is needed. These are not mutually exclusive ideas: a system could use a primitive-first
domain model and Cordis-like dynamic composition at a lower runtime layer. The interesting empirical question is
whether the richer runtime is necessary for the common agent workload or whether it is solving a more general problem
than the workload requires.

The recent convergence study of coding-agent harnesses further strengthens the research direction. If independent
systems converge on durable sessions, a commoditized loop, progressive context disclosure, model-specific data, and
explicit extension seams [16], then the next question is not simply “which framework has the most features?” It is “which
architectural representation makes those recurring semantics easiest to understand, evolve, and generate?”

14. Conclusion
This paper proposes and operationalizes a Primitive-First Architecture for LLM agent systems. Its central idea is
simple: identify stable semantic primitives before adding abstractions; keep internal variation as injectable policy; use
composition for larger behavior; and use contract-preserving layers for single-axis cross-cutting concerns.

For the studied class of turn-based tool-using agents, AgentCore demonstrates a concrete realization using reasoning,
acting, and remembering contracts. The supplied source audit shows a small implementation and several extensions that
remain outside the execution kernel. The comparison with LangGraph, Microsoft Agent Framework, Pydantic AI, OpenAI
Agents SDK, and DeepSeek Harness/Cordis shows that the research question is not “which framework has fewer lines?”
but “what architectural ontology is required to express a capability, and how much disturbance does that ontology impose
when requirements evolve?”

The paper deliberately rejects a universal minimalism claim. The adversarial analysis identifies primitive insufficiency,
cross-primitive transactions, layer-order dependence, substrate leakage, and AI-facing semantic requirements as
meaningful boundaries. These limitations are essential because they turn the proposal into a falsifiable research program
rather than a design manifesto.

The current evidence is sufficient for a research manuscript and reproducible preprint draft, but not for claiming causal
superiority: the controlled extension, evolution, AI-agent, and defect-locality experiments remain to be executed. The next
empirical step is therefore clear. Freeze the primitive criteria, implement standardized tasks against matched baselines,
collect architectural disturbance and AI implementation metrics, and test whether the observed advantage survives
independent replication.

If the hypotheses survive those experiments, the contribution would be more than an AgentCore design. It would be
evidence for a general engineering principle for AI-assisted software development: architectural simplicity is achieved
less by writing less code than by choosing representations that make unnecessary code unnecessary.

• Freeze framework commits/versions and record exact commit hashes.

• Publish the source-audit scripts used to count code and classify architectural elements.

• Publish the task specifications for the five controlled experiments.

• Use identical task requirements across frameworks and distinguish framework code from application code.
